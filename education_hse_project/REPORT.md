# Разбор ошибок исходного анализа и исправленные выводы

Документ описывает, что было не так в `hse_project.ipynb`,
`hse_project-ver2.ipynb`, `hse_project-ver3.ipynb`, как это исправлено
и какие выводы получаются на корректно обработанных данных.

Исправленный анализ: [`hse_project_fixed.ipynb`](hse_project_fixed.ipynb),
код — в `src/`, воспроизведение — `python run_analysis.py`.

## Часть 1. Ошибки, ломавшие результат

### 1.1. Обнуление строк целиком вместе с целевой переменной

Ячейки 20, 21, 39 — во **всех трёх** версиях:

```python
data.loc[data['fulltime'] == 'undefined'] = 0
data.loc[data['fulltime'] == 'nun'] = 0
data.loc[data['firstclick'] == 'undefined'] = 0
```

Пропущено указание столбца. `data.loc[mask] = 0` присваивает ноль **всей
строке**, а не одной ячейке. Правильно было бы
`data.loc[mask, 'fulltime'] = 0`.

Последствия (`python bug_impact.py`):

| | |
|---|---|
| строк обнулено целиком | **388 из 2796 (13.9 %)** |
| из них имели `GGlevel != 0` | **309** — им целевая переменная переписана на 0 |
| доля `GGlevel = 0` в выборке | выросла с 17.6 % до 28.7 % |
| во что превратились обнулённые строки | **одна** уникальная строка из нулей |

Модель тривиально отделяет 388 одинаковых нулевых строк, все помеченные
уровнем 0. Это чистый искусственный сигнал. На той же исправленной
методике одна эта ошибка завышает accuracy на **+6.6 процентного пункта**
(0.618 против 0.552).

### 1.2. Сравнение несравнимых метрик в проверке на адекватность

Ячейка 114, во всех трёх версиях:

```python
ac_dmc   = dmc.score(x_test, y_test)     # accuracy классификатора
accuracy = model.score(x_test, y_test)   # R² линейной регрессии
print("Качество наивного прогноза :", ac_dmc)    # 0.245
print("Качество нашего прогноза :", accuracy)    # 0.649
```

`LinearRegression.score` возвращает **коэффициент детерминации**,
`DummyClassifier.score` — **долю верных ответов**. Это разные шкалы и
разный смысл. Вывод «0.65 против 0.25, значит модель адекватна» ни из чего
не следует — проверки на адекватность в работе фактически не было.
Переменная вдобавок названа `accuracy`, хотя хранит R².

### 1.3. Численно вырожденная модель в первой версии

Вывод ячейки 110 в `hse_project.ipynb`:

```
RuntimeWarning: divide by zero encountered in matmul
RuntimeWarning: overflow encountered in matmul
RuntimeWarning: invalid value encountered in matmul
```

Матрица признаков вырождена, коэффициенты ушли в бесконечность. При этом
именно на график этих коэффициентов опирается список «10 ключевых
параметров» в выводах работы.

Там же, ячейка 124 (тест Бартлетта): `divide by zero encountered in det` —
определитель корреляционной матрицы нулевой. Значит χ² = 59396 недостоверен,
хотя истолкован как статистически значимый.

### 1.4. Последовательности действий, закодированные как числа

Столбцы `savepicture`, `picturechoose`, `picturechoosedelete`,
`citationcode` хранят **последовательности** кликов. Excel в русской
локали исказил их тремя способами:

| в файле | что это на самом деле | как исказил Excel |
|---|---|---|
| `'2,4,5'` | последовательность 2 → 4 → 5 | уцелело |
| `2.4` | последовательность 2 → 4 | запятая прочитана как десятичный разделитель |
| `'5.0999999999999996'` | последовательность 5 → 1 | то же + шум представления float |
| `Timestamp('2024-01-02')` | последовательность 2 → 1 | прочитано как дата «2 января» |

Дат оказалось **425 штук**; у всех день и месяц лежат строго в диапазоне
1–8, то есть ровно в алфавите кодов картинок — гипотеза проверяема.

Исходная работа подавала всё это в `OrdinalEncoder` как строки:
`'1,2,3'` получал код 7, `Timestamp('2024-01-02')` — какой-то другой,
после чего они участвовали в линейной регрессии как **величины**. Это же
и порождало вырожденность из п. 1.3 — сотни уникальных «категорий» на
2241 наблюдение.

### 1.5. `'undefined'` как полноценная категория

Пропуск в выгрузке закодирован тремя способами: пустая ячейка, строка
`'undefined'` и опечатка `'nun'`. Исходная работа обрабатывала только
`NaN` — `'undefined'` доживал до кодировщика и становился обычной
категорией наравне с «почта» и «поиск».

### 1.6. Ordinal-кодирование номинальных признаков

`firstclick` (почта / поиск), `commtypes` (7 типов сообществ), `commname`
и прочие — категории без порядка. `OrdinalEncoder` присваивает им номера
по алфавиту, после чего линейная модель считает, что «Бизнес» (0) →
«Бренд» (1) → «Мероприятие» (2) образуют шкалу с равными шагами.
Коэффициент при такой переменной не интерпретируем. README обещал
one-hot, но в коде его не было.

### 1.7. Целевая переменная внутри факторного анализа

В `hse_project.ipynb`: `df_cc = df.copy()` — вместе с `GGlevel`
(39 собственных значений против 38 признаков). Фактор №1 вбирал в себя
ту самую оценку, которую должен был объяснять. В ver2/ver3 исправлено.

### 1.8. Неверный подсчёт числа факторов

Собственные значения из ячейки 131 первой версии:

```
15.79, 2.47, 2.13, 1.65, 1.43, 1.24, 0.9998, 0.92, ...
```

Больше единицы — **шесть** значений, седьмое равно 0.9998. В тексте
написано «Выделим 8 факторов с собственным значением больше 1», и взято 8.
В ver2/ver3 (5 значений выше единицы, взято 5) — верно, но заголовок там
остался от первой версии: «корреляционную матрицу между вопросами и
полученными **восьмью** факторами» при `n_factors=5`.

### 1.9. Потеря знака факторных нагрузок

```python
loadings = np.abs(loadings)
```

После взятия модуля направление связи потеряно. Вывод «фактор №1
оказывает **повышающее** влияние» после этой строки не опирается на
данные.

### 1.10. Сравнение средних по порядковым кодам

Вывод «балл фактора 5.16 выше общего 2.69» сравнивает средние по столбцу
`ср.знач`, где усреднены произвольные коды категорий из п. 1.4 и 1.6.
Среднее по номерам категорий — число без интерпретации.

Вдобавок `ср.знач` приклеивается к таблице нагрузок через
`pd.concat(..., axis=1, join="inner")` **по позиции**, а список из 39 имён
в ячейке 143 набран вручную: при любом расхождении с порядком
`df.columns` значения молча съезжают на соседние строки.

## Часть 2. Ошибки методики

### 2.1. Отсутствие `random_state`

`train_test_split` вызывался без фиксации seed. Результаты
не воспроизводятся: baseline `most_frequent` на одних и тех же данных даёт
0.316 в ver2 и 0.327 в ver3. Значит и список «топ-10 признаков» менялся от
запуска к запуску.

### 2.2. Валидационная выборка не использовалась

`x_valid` / `y_valid` создавались, но обращалась к ним только
закомментированная логистическая регрессия (ячейка 107). Модель обучалась
на train и сразу оценивалась на test — отбора модели не было, а тестовая
выборка выполняла роль валидационной.

### 2.3. Listwise deletion 20 % выборки

`dropna` по цепочке столбцов сократил выборку с 2796 до 2241. Пропуски
здесь не случайны: кто не ответил на `private4`, скорее всего слабее в
задании. Удаление таких респондентов смещает выборку в сторону сильных —
а модель как раз и должна отличать сильных от слабых.

### 2.4. Задача решалась регрессией вместо классификации

`GGlevel` — порядковая метка из четырёх уровней, а не непрерывная
величина. `LinearRegression` предсказывала дробные значения, метрикой был
R², сравнение шло с классификатором (п. 1.2).

### 2.5. Признаки не масштабировались

Время в минутах (десятки) соседствовало с кодами ответов (0–3). Сравнивать
величины коэффициентов при таких признаках нельзя.

### 2.6. Ошибка в подсчёте доли коррелирующих пар

```python
df.corr(method='spearman').unstack().sort_values(ascending=False).drop_duplicates()
```

`drop_duplicates()` отбрасывает дубликаты **по значению корреляции**, а не
зеркальные пары: две разные пары признаков со случайно совпавшим значением
схлопываются в одну. Диагональ (корреляции 1.0) тоже участвует. Полученные
«3 %» — не та величина, которую хотели посчитать.

### 2.7. Критерий Кайзера для выбора числа факторов

«Собственное значение больше 1» систематически завышает число факторов.
Корректный способ — параллельный анализ Хорна.

### 2.8. Факторный анализ на порядковых кодах

KMO, тест Бартлетта и `FactorAnalyzer` работают с корреляциями Пирсона и
предполагают переменные, для которых расстояние осмысленно. К номинальным
категориям это неприменимо.

### 2.9. Мелочи

* Ячейка 17: `round(isna_sum / 2405 * 100, 2)` — знаменатель 2405 при 2796
  строках в кадре, доли пропусков посчитаны неверно.
* Ячейки 87–90: `astype(int)` применяется дважды вокруг деления на 60,
  время режется до целых минут.
* Заголовок ячейки 81 перечисляет `private5`, `private6`, `wall3`,
  `wall4`, `copymail`, но код их не обрабатывает.

## Часть 3. Что сделано в исправленной версии

| Было | Стало |
|---|---|
| `data.loc[mask] = 0` — обнуление строк | точечная замена, целевая переменная неприкосновенна (есть тест) |
| `'undefined'` — категория | все три кодировки пропуска сводятся к `NaN` |
| последовательности → `OrdinalEncoder` | парсер трёх искажений Excel → длина, число повторов |
| номинальные → ordinal-коды | one-hot |
| `dropna`, −20 % выборки | все 2796 строк, индикаторы пропуска |
| `LinearRegression` + R² | классификация, 4 метрики включая взвешенную каппу |
| R² против accuracy | одни и те же метрики для всех моделей |
| нет `random_state` | зафиксирован везде |
| валидация не используется | 5-fold CV для отбора, тест — один раз в конце |
| коэффициенты без масштабирования | permutation importance + стандартизованные коэффициенты |
| критерий Кайзера | параллельный анализ Хорна |
| FA на всех столбцах | FA на числовом блоке, MCA на номинальном |
| `np.abs(loadings)` | нагрузки со знаком |
| целевая переменная внутри FA | исключена, `GGfscore` исключён как утечка |

Препроцессинг целиком лежит внутри `sklearn`-пайплайна, поэтому импутация
и масштабирование обучаются только на обучающем фолде.

## Часть 4. Исправленные выводы

### 4.1. Модель работает, но скромнее заявленного

Отложенная выборка, одинаковые метрики для всех моделей:

| модель | accuracy | macro-F1 | взвеш. каппа | MAE (уровни) |
|---|---|---|---|---|
| baseline «самый частый класс» | 0.332 | 0.125 | 0.000 | 0.845 |
| baseline «случайно по частотам» | 0.254 | 0.239 | −0.002 | 1.120 |
| **логистическая регрессия** | **0.552** | **0.562** | **0.672** | **0.500** |
| случайный лес | 0.532 | 0.540 | 0.643 | 0.513 |
| градиентный бустинг | 0.523 | 0.533 | 0.656 | 0.527 |

Модель уверенно превосходит базовую — впервые по сопоставимой метрике.
Взвешенная каппа 0.67 означает существенное согласие с истинными уровнями,
средняя ошибка — половина уровня. Исходные «0.65 против 0.25» были R² на
испорченных данных.

### 4.2. Два разных вида пропуска, которые нельзя смешивать

В топе permutation importance стоят `copymail_is_empty` и индикаторы
пропуска. Но проверка показала, что за ними стоят **два разных явления**.

**Сбой логирования** (`fulltime`, `openglasha`, `notion` не записаны,
14–16 % респондентов). Доля таких записей по уровням: 0.122 / 0.137 /
0.154 / 0.140 — связи с уровнем **нет** (χ², p = 0.42). Индикатор важен
модели как переключатель «здесь данных нет», а не как маркер
компетентности: его удаление почти не меняет качество (accuracy
0.552 → 0.548). На таких респондентах модель ставит всем модальный класс
и даёт accuracy 0.341; на респондентах с исправным логом — **0.593**.

**Недоведение задания до конца** (`copymail_is_empty` 38.5 % → 15.6 %,
`private6` и `wall4` без ответа 31 % → 14 %). Вот это уже содержательный
сигнал, монотонный по уровню.

Первая ось MCA (97 % инерции) отражает именно первое явление —
техническое, а не поведенческое.

### 4.3. Содержательная компетентность существует и измерима

Вторая ось MCA коррелирует с непрерывным баллом `GGfscore` на
**ρ = −0.70** (с `GGlevel` — −0.68), будучи построенной **без обращения
к целевой переменной**. Это честная внешняя валидация структуры.

Её полюс низкой компетентности собран из небезопасных решений:

* `private2` — «О, прикольно, пусть все посмотрят этот сайт!»
  (переслать подозрительную ссылку дальше);
* `wall4` — «Давайте все напишут свои номера телефонов, а мы им позвоним»
  (публикация персональных данных);
* `commtypes` — «Бизнес» вместо сообщества по интересам.

То есть измеряемый конструкт — это **безопасное поведение в сети**, и он
воспроизводится из логов.

### 4.4. Единого поведенческого фактора нет

Факторный анализ числового блока:

* **KMO = 0.51** — ниже общепринятого порога 0.6. Общей факторной
  структуры в поведенческом блоке практически нет.
* Параллельный анализ Хорна даёт 6 факторов (критерий Кайзера дал бы 7).
* Все шесть факторов **лишь группируют признаки одного происхождения**:
  фактор 2 — всё про `picturechoose`, фактор 3 — всё про `citation`,
  фактор 4 — всё про `savepicture`. Это артефакт конструирования
  признаков, а не латентная компетентность.

Время выполнения, число вызовов ассистента и число сохранённых картинок
не складываются в общую способность.

**Утверждение исходной работы** — что существует фактор №1, объединяющий
умение настраивать сообщество, отвечать в личных сообщениях и отвечать на
комментарии, — **не подтверждается**. Оно возникло из трёх наложившихся
дефектов: вырожденной корреляционной матрицы (п. 1.3), участия целевой
переменной в анализе (п. 1.7) и произвольного кодирования категорий
(п. 1.4, 1.6). Числа «5.16 против 2.69», на которые опирался вывод,
интерпретации не имеют (п. 1.10).

### 4.5. Что ограничивает выводы

* **Порог компетентности задан инструментом.** `GGlevel` — результат
  дискретизации `GGfscore`, посчитанного авторами методики по этим же
  ответам. Модель воспроизводит их шкалу, а не внешний критерий.
* **Ключа правильных ответов нет.** Поэтому ответы кодируются номинально,
  а не как «верно / неверно». MCA обходит это ограничение, но связь
  «полюс оси = правильный ответ» установлена содержательно, а не по ключу.
* **Пропуск смешивает две причины** — респондент не дошёл до задания или
  не совершил действия осознанно. Логи не позволяют их разделить.
* **Потолок качества.** Три разных семейства моделей упираются в
  accuracy 0.52–0.55. Похоже, это предел того, что извлекается из данного
  набора логов.
